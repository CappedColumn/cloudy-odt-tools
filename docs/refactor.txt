  Rework codt-tools into four clear layers:

  1. case
  2. run
  3. simulation
  4. registry optional

  The package should feel like:

  - Case describes a CODT setup completely
  - Run stages and executes one concrete case with one executable
  - Simulation reads outputs and analyzes them
  - Registry is a side utility, not part of the required workflow

  That is a much better fit than the current coupling between config.py, runner.py, experiment.py, and registry/api.py.


  Proposed Package Layout

  codt_tools/
    case/
      __init__.py
      case.py
      namelist.py
      aerosol.py
      parcel.py
      mutate.py
      validate.py
      io.py

    run/
      __init__.py
      run.py
      local.py

    simulation/
      __init__.py

    compat/
      __init__.py

  You do not need to physically split it this way on day one, but this should be the architectural target.

  Core API

  The new API should optimize for the common workflow first.

  from codt_tools.case import Case
  from codt_tools.run import Run
  from codt_tools.simulation import Simulation

  case = Case.from_input_dir("CODT/input")
  case.params.set(tref=21.0, tmax=3600.0)
  case.aerosol.set(injection_rate=[6.6e4])

  run = Run(
      case=case,
      executable="/path/to/CODT",
      workdir="/scratch/general/vast/$USER/codt/test1",
  )

  run.stage()
  run.execute_local()

  sim = Simulation.from_run(run)
  sim.plot_timeseries("LWC")

  And for multiple cases:

  cases = case.sweep({
      "params.tref": [20.0, 21.0, 22.0],
      "aerosol.injection_rate": [[5e4], [6e4], [7e4]],
  })

  runs = [
      Run(case=c, executable="/path/to/CODT", workdir=f"/scratch/.../run_{i}")
      for i, c in enumerate(cases)
  ]

  Module Responsibilities

  case

  - Own all input data needed for one CODT run
  - Include namelist, aerosol input, parcel input
  - Support load, edit, validate, copy, write
  - Never know about SLURM
  - Never know about registries
  - Never mutate itself implicitly during unrelated operations

  This directly fixes the current hidden mutations in CODTConfig.write():1431 and CODTRunner.setup_run():194.

  Suggested class model:

  class Case:
      params: NamelistModel
      aerosol: AerosolModel
      parcel: ParcelModel | None

      @classmethod
      def from_input_dir(...)
      def clone(...)
      def write_inputs(...)
      def validate(...)
      def apply(...)
      def sweep(...)

  run

  - Own one Case plus one executable plus one working directory
  - Stage inputs into a run directory
  - Execute locally
  - Optionally generate simple SLURM launch artifacts
  - Optionally perform lightweight executable validation

  The run layer should not require account, partition, or qos in its constructor. Those are cluster policy, not run semantics.

  Suggested model:

  class Run:
      case: Case
      executable: Path
      workdir: Path

      def stage(self) -> Path
      def execute_local(self) -> CompletedProcess
      def generate_slurm_launcher(self, ...) -> Path
      def open_simulation(self) -> Simulation

  simulation

  - Keep most of today’s CODTSimulation
  - Move it under a dedicated namespace
  - Keep analysis read-only
  - Add helpers like Simulation.from_run(run)

  simulation.py is already close to this shape.

  registry

  - Optional utility only
  - Record that runs happened
  - No lifecycle orchestration
  - No required hooks inside Run.execute_local() or SLURM scripts
  - No experiment tree creation
  - No relocation workflow

  A minimal schema is enough:

  - run_id
  - case_name
  - workdir
  - executable_path
  - executable_version
  - input_hash
  - created_at
  - notes
  - tags

  This is much smaller than the current registry in registry/api.py:71.

  How Sweeps Should Work

  This is the biggest functional redesign.

  Current issue:

  - CODTConfig.sweep():1788 only changes namelist parameters

  New behavior:

  - sweeps should support the whole case, not just namelist values

  Use path-based mutation:

  case.sweep({
      "params.tref": [20.0, 21.0],
      "params.volume_scaling": [13, 50],
      "aerosol.injection_rate": [[6.6e4], [8.0e4]],
      "parcel.velocity": [[1.0, 0.5], [0.8, 0.4]],
  })

  Also allow callable mutators for harder cases:

  def seeded_variant(case):
      c = case.clone()
      c.aerosol.set_seed_group(...)
      c.params.set(do_seeding=True)
      return c

  That removes the current mismatch between the conceptual “simulation sweep” and the actual implementation.

  SLURM Design

  Keep SLURM support, but narrow its job.

  codt-tools should generate one of these:

  1. A plain launcher shell script:

  /path/to/CODT /path/to/run1/inputs/params.nml
  /path/to/CODT /path/to/run2/inputs/params.nml
  ...

  2. A simple parallel launcher:

  /path/to/CODT run1/inputs/params.nml &
  /path/to/CODT run2/inputs/params.nml &
  wait

  3. An array-ready task file plus template script:

  - runs.txt with one namelist path per line
  - slurm_template.sh that reads line SLURM_ARRAY_TASK_ID

  Do not bake CHPC policy into the core module:

  - no hard-coded account logic
  - no partition introspection inside the base Run
  - no registry CLI calls embedded into batch scripts

  A small helper in run/slurm.py can still emit a generic template with placeholders:

  #SBATCH --account=<ACCOUNT>
  #SBATCH --partition=<PARTITION>
  #SBATCH --time=<TIME>
  #SBATCH --nodes=1
  #SBATCH --ntasks=1

  CODT_EXE="<EXECUTABLE>"
  NAMELIST="$(sed -n "$((SLURM_ARRAY_TASK_ID + 1))p" runs.txt)"
  "$CODT_EXE" "$NAMELIST"

  That is much simpler and more portable than the current deeply integrated runner in runner.py.

  Executable Validation

  Add a small utility in run/validate_exec.py.

  Goal:

  - make architecture-tuned builds easy to validate before a big campaign

  Suggested checks:

  - executable exists
  - --version works
  - optional build-arch detection
  - optional smoke-case generation and dry local run
  - report as a plain Python object or JSON

  Example:

  report = validate_executable(
      executable="/path/to/CODT",
      smoke_case=Case.from_input_dir("CODT/input"),
  )

  That solves a real need without dragging registry/SLURM into the path.

  Refactor Strategy

  Phase 1: Stabilize the current code

  - Keep existing public imports in __init__.py
  - Add tests around current CODTConfig, CODTRunner, and CODTSimulation
  - Mark experiment and full registry workflow as advanced/legacy in docs

  Phase 2: Introduce the new core API

  - Add Case, Run, and Simulation wrappers
  - Internally reuse existing code from config.py and simulation.py
  - Keep behavior explicit: stage() writes files, execute_local() runs, nothing else hidden

  Phase 3: Replace sweep logic

  - Implement path-based mutation
  - Support aerosol and parcel sweeps
  - Deprecate direct reliance on CODTConfig.sweep():1788

  Phase 4: Simplify SLURM

  - Replace the current cluster-aware all-in-one submission path with:
      - generate_launcher()
      - generate_slurm_template()
      - optional submit(command="sbatch ...") helper only if desired
  - Move CHPC-specific logic into docs or a separate helper module, not the core API

  Phase 5: Shrink the registry

  - Create a minimal optional registry
  - Remove registry hooks from normal run execution
  - Deprecate experiment tree orchestration in experiment.py

  Concrete Developer Guidance

  When rewriting, use these rules:

  - A Case must be a pure in-memory description of inputs
  - Writing files must not silently rewrite unrelated user intent except for explicit staging paths
  - Running locally must require only:
      - case
      - executable
      - workdir
  - SLURM generation must output simple artifacts, not own cluster policy
  - Analysis must remain independent of execution machinery
  - Registry must never be required to run or analyze CODT

  Best End State

  The elegant version of codt-tools is one where:

  - setting up a case is obvious
  - running one case locally is trivial
  - generating many runs is explicit and flexible
  - SLURM support is helpful but minimal
  - analysis is clean and stable
  - provenance is optional, not structural

  This migration map should be treated as a strong suggestion, not a rigid prescription. If, while refactoring, there is a cleaner path that preserves behavior and reduces complexity faster, that is the better choice. The goal is not to preserve the current structure; the goal is to arrive at a
  simpler, more elegant codt-tools with minimal user pain.

  Migration Principle

  Use a “strangler” approach:

  1. Keep the current package installable and testable.
  2. Introduce the new API alongside the old one.
  3. Move behavior behind the new interfaces incrementally.
  4. Deprecate old entry points only after the new path is clearly better.

  That is likely simpler and safer than trying to rewrite everything in place.

  Compatibility Layer

  Create a temporary compat/ layer.

  Suggested files:

  - compat/legacy_config.py
  - compat/legacy_runner.py

  These can:

  - preserve CODTConfig
  - preserve CODTRunner

  Suggested Migration Order

  1. Extract stable low-level models first
      - namelist
      - aerosol
      - parcel
      - validators
  2. Introduce Case
      - wrap existing pieces without redesigning everything at once
  3. Introduce Run
      - local execution first
      - explicit staging
      - no registry integration
  4. Adapt Simulation
      - mostly namespace cleanup
  5. Rebuild sweep behavior
      - path-based mutations
      - aerosol/parcel-aware
  6. Add simple SLURM artifact generation
      - scripts and manifests only
  7. Shrink or replace registry
      - only after core run path is clean
  8. Deprecate legacy APIs
      - once tests and docs are stable

  Places Where You Should Feel Free To Deviate

  This map is worth altering if any of these turns out true:

  - keeping config.py intact but introducing Case as a wrapper is simpler than immediate splitting
  - a tiny campaign.py is useful for sweeps, without reviving full experiment orchestration
  - JSONL is cleaner than SQLite for the minimal registry
  - a single run.py is simpler than splitting run/local.py, run/stage.py, and run/slurm.py initially

  Those are all good simplifications if they reduce moving parts without reintroducing hidden coupling.

  One Good Minimal First Refactor

  2. Add:

      - codt_tools/run.py

  3. Implement new APIs there by reusing current internals.

  Bottom Line

  The safest elegant migration is:

  - new API first
  - internal cleanup second
  - legacy removal last

  If the coder finds a simpler route than this map while preserving that principle, they should absolutely take it.

  I’d keep this in the same repository and do the transition in a small number of reviewable branches, with commits grouped by architectural intent rather than by file churn.

  How Big Should Each PR Be?

  Ideal PR size:

  - 300 to 800 meaningful lines changed if possible
  - one architectural idea per PR
  - avoid mixing docs, registry, SLURM, and sweeps unless tightly related

  A good practical split is:

  1. PR 1: tests plus new Case and Run
  2. PR 2: sweep redesign
  3. PR 3: simple SLURM launcher generation
  4. PR 4: minimal registry
  5. PR 5: docs and deprecations

  That is probably the cleanest balance.

  What Not To Do

  Avoid these patterns:

  - one giant “rewrite codt-tools” branch
  - commits that both move files and heavily rewrite logic at the same time
  - deleting legacy APIs before the new ones are documented and tested
  - mixing CHPC policy decisions into the new core Run API

  A Very Simple Solo-Developer Version

  Suggested GitHub Milestone Format

  Milestone: codt-tools simplification

  Issues or tracked items:

  1. Core API: Case/Run/Simulation
  2. Whole-case sweeps
  3. Simple SLURM launcher generation
  4. Optional minimal registry
  5. Legacy API deprecation
  6. README and migration guide

  Definition of Done

  The milestone is done when:

  - local CODT runs use Case and Run
  - sweeps can mutate aerosol and parcel inputs
  - SLURM support is artifact generation, not cluster-policy orchestration
  - the registry is optional and minimal
  - Simulation remains stable for analysis
  - docs teach the new workflow first
  - legacy APIs are either shimmed or clearly deprecated

  Important Flexibility Note

  This plan is intentionally structured, but it should not become dogma. If, during PR 1 or PR 2, it becomes obvious that a simpler path exists, especially one that keeps compatibility while reducing code movement, that is preferable to following this plan mechanically. The repo history should serve
  the redesign, not control it.
